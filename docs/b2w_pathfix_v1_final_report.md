## 0. 一句话结论

**训练没有崩，但它收敛到了一个"停在目标附近刷分"的局部最优**：每回合总收入里"目标附近"从 13.0 涨到 34.2，
而"完成目标"从 8.4 掉到 5.4（比值 1.54 → 6.38）。路径项的收入**根本没有变**（13.1 → 13.0），

换言之：**策略学会了在目标周围绕圈换钱，而不是走完路径**。

## 2. 机制：为什么"绕圈"是严格最优

`dt = 0.2 s`，所有密度项都被奖励管理器乘 `dt`：

| 行为 | 每步收入 | 出处 |
|---|---:|---|
| 沿路径行驶（1.2 / m @ 0.83 m/s） | 1.2 × 0.83 × 0.2 = **0.20**（且只有 d<0.8 的段才付） | `rewards.py:progress_along_path` |
| 圈内 d≈0.3：`reach_goal` | 2.0 × 0.2 = **0.40** | `rewards.py:285`，**无速度门** |
| 圈内 d≈0.3：`tight` 1/(1+(0.3/0.25)²)/0.2 ×0.75 ×0.2 | **0.39** | `navigation_env_cfg.py:89-104` |
| 圈内 d≈0.3：`soft` 1/(1+(0.3/2.5)²)/1.0 ×0.25 ×0.2 | **0.05** | 同上 |
| **圈内合计** | **0.84 / 步** | 实测 34.24 / 40.1 步 = 0.85 ✓ |
| 完成驻留（8 步 ×0.84）+ 一次性奖励 | **+25，然后回合结束** | `goal_reached_bonus = 25` |

一圈 90 s 有 450 步。停在/绕着目标 = 0.84 × 剩余步数；完成 = +25 就没了。
**只要"目标附近每步收入 > 0"，完成就永远是坏选择**——这是结构性的，不是调参问题。
实测每回合 40 步圈内收入 34.2，等价于 1.4 次"完成奖励"，而它宁愿不完成。

> 这条与 `docs/b2w_pathfix_v1_training_analysis_2026-11-26.md` 的判断一致，本报告给出的是 4000 iter 结束时的确认。

## 3. 路径跟踪其实没坏——被吃掉的是"步数"

这一节修正了一个流传很广的读法（包括 `…_analysis_2026-11-26.md` 的 B1/B5 定位）：

| 证据 | 训练口径（带观测噪声 + push） | 干净 eval（Play 协议，model_3999） |
|---|---:|---:|
| 每步 `distance_to_path` 的中位数 | ~0.95 m（由偏差惩罚反推，**下界**） | **0.36 m**（p90 0.66） |
| 每回合被付费的路径米数 | 10.8 m（计划路径 ~24 m） | — |
| 实际行驶 / 计划路径 | — | 27.8 / 20.7 = **1.34 倍** |
| 进入过 0.5 m 圆的回合 | — | **54%** |
| 真正完成 1.5 s 驻留的回合 | 21.5%（bonus 口径） | **10.5%** |
| 跑满 horizon 的回合 | `time_out` 0.367 | **71%** |

也就是说：**路径是跟得住的**（干净条件下横向误差 0.36 m，远在 0.8 m 支付门内）。
路径项收入 13.0 一直没涨，不是"支付门把它挡住了"，而是**回合里 71% 的时间耗在目标附近空转**——
空转的步数是零路径进度的。把回合从 119 步拉到 286 步的，正是这一段。

几何层面的问题仍然存在，但它们是次要项（`invalid_seg_frac` 0.22、`blocked_episode` 0.15 vs 期望 0.37、
`repair_corner_chords` 是死代码、重采样切角 ≤0.2 m），**不影响本 run 的结论**，放在 P2。

## 6. 干净 eval（Play 协议：无观测噪声、无外力；200 局，actor 1）

同一套脚本、同一口径（驻留完成才算成功）。旧策略 = `b2w_sigma_bounded/model_6000.pt` + `--legacy_env`。

| 指标 | **旧策略 60 s**（基线） | **新策略 60 s** | **新策略 90 s** |
|---|---:|---:|---:|
| SR（驻留口径） | **0.480** | **0.105** | 0.120 |
| SR（锁存口径，旧日志可比） | 0.490 | 0.540 | 0.560 |
| SPL | 0.339 | 0.043 | 0.049 |
| median d_path | **1.19 m** | **0.36 m** | 0.36 m |
| p90 d_path | 2.17 m | 0.68 m | 0.68 m |
| 实际行驶 / 计划路径 | 15.4 / 25.5 = 0.60 | 27.8 / 20.7 = **1.34** | 32.6 / 21.0 = 1.55 |
| 跑满 horizon 的回合 | 0.395 | **0.710** | 0.640 |
| 圈内速度 p50 | **0.48 m/s** | **1.10 m/s** | 1.08 m/s |
| 每回合圈内步数（中位） | 0 | 3 | 10 |

**三句话读这张表：**

1. **路径层成功了**：中位横向误差 **1.19 → 0.36 m**，p90 2.17 → 0.68。旧策略是"抄近路"，新策略是"贴线走"。
   这正是本次改版要的东西，而且是在干净协议下测的，不是训练口径的估计。
2. **终点行为崩了**：旧策略以 **0.48 m/s** 进圈、按 8 步驻留完成（0.48）；新策略以 **1.10 m/s** 冲进圈，
   在圈里绕 19 s，**只完成 10.5%**。两者相差的不是"能力"，是"动机"——旧奖励里进圈没有持续收入，
   新奖励每分钟付 0.84/步。
3. **旧基线 0.580（锁存）≈ 0.480（驻留）**：旧策略本来就刹得住，所以锁存口径没有灌水。
   也就是说 **0.480 是真实可用的基线**，"SR ≥ 0.58" 这个验收门槛是合理的、可达的。

> 顺带修掉一个测量 bug：`eval_policy.py` 原来用 `steps < max_episode_length` 判断"提前结束"，
> 而满回合记录的是 `max_episode_length - 1`，于是**每次超时都被当成提前结束**，SR 悄悄退化成锁存口径
> （旧 run 的 `sr == sr_old_rule` 就是这个 bug 的指纹）。现已修正，并新增圈内步数 / 圈内速度 /
> 最长驻留连击三个诊断量。

**口径注意**：旧策略只能用 `--legacy_env` 评（它期望 60 维路径观测），所以两行的“计划路径”本身不同
（legacy 管线 25.5 m vs v2 管线 20.7 m），`d_path` 的对比里含一部分“路径本身更好”的成分，不纯是策略差异。
但方向与量级足以说明问题：旧策略对自己那条路径的中位偏离 1.19 m，新策略对 v2 路径 0.36 m。

**一个很说明问题的细节**：新策略 200 局里最长驻留连击的分布是
`0 步 93 局 / 6 步 22 局 / **7 步 53 局** / 8 步 17 局`。也就是说它绕圈的周期**刚好让它在 0.5 m 圆里擦过 7 步**——
距离成功只差一步，但它没有任何理由去补那一步（补上就要结束回合，丢掉 0.84/步的流水）。
旧策略的分布是 `7 步 18 局 / 8–11 步 79 局`：它会停下来，所以稳稳越过门槛。

## 10. 现场观察到的两个新失效模式（2026-11-26，play 交互）

这两条是**看 play 录像/操作**发现的，训练标量与 eval 聚合指标都不会直接报警（它们表现为"某一类几何条件下的静止"，
被平均掉了）。必须写进规格，因为 P1 修完只会让它们更明显：P1 之后，停在原地**一分钱都拿不到**。

### 10.1 大角度起始朝向 → 原地不动 / 缓慢倒走

**现象**：
- 机器人初始朝向与路径起始切线（或最终目标方向）相差很大（接近 180°）时，会**原地不动**，或极缓慢倒走；
- 当机器人朝向与**终点朝向**相近、但与**路径起始方向**差别大时，同样会僵住。
- 加路径层之前没有这个现象——那时机器人可以边探索边把身子转过来。

**代码层面的直接原因（已核实）**：

| 事实 | 位置 |
|---|---|
| 出生 yaw 是 **±180° 均匀随机**，与路径方向无关 | `navigation_env_cfg.py:279` `reset_root_state_uniform`，`pose_range["yaw"]=(-π, π)` |
| 因此**约一半回合**一出生路径就在身后，必须原地转身才能开始 | 同上 |
| 奖励里**没有任何一项为"转身/对齐"付钱**：`progress_along_path` 只认沿路位移，`progress` 只认向目标投影 | `rewards.py`，`B2WRewardsCfg` 14 项 |
| 仓库里有 `heading_alignment`（对齐目标的余弦形函数），但 **B2W 的 v2 奖励表没有用它** | `rewards.py:246`，`navigation_env_cfg.py:45-110` |
| 原地转身要付 `action_rate_l1`（−0.02）与 `joint_acc_l2_joint` 的代价，收益为 0 | `B2WRewardsCfg` |

于是"站着不动"在数值上几乎是零成本零收益；转身的收益要等到**转过之后**才能兑现，属于延迟奖励，
PPO 很难在没有正向引导的情况下自己发现。旧奖励里"朝目标方向的投影进度 + gated heading"给了这个梯度，
v2 把方向项换成了路径弧长，梯度一起消失了。

**候选修复（按推荐度）**：

1. **出生朝向与路径起始切线对齐**（±90° 内随机，另留 10% 全随机保留鲁棒性）——最便宜、不引入新的
   奖励面。部署时操作员本来就可以把机器人朝着路径放。
2. **给"朝向路径切线"一个小的稠密项**（复用 `heading_alignment`，把目标方向换成路径切线），并且
   **只在有前进速度时给**——否则又是一个"站着不动也能刷分"的旅馆（这次刷的是朝向）。
3. 降低转身的动作代价（`action_rate` 权重），只在确认是动作惩罚导致僵住时做。

**怎么确认**：在 play 里记录每个 stall 时刻的 `‖v‖`、`episode_length_buf`、路径切线在机体系的夹角、
以及 `progress_along_path` 的最近 N 步是否恒 0。若夹角 > 120° 且速度 ≈ 0 且 progress 恒 0 → 10.1 成立。

### 10.2 楼梯：从左转到上楼梯再到右转时，停在楼梯前

**现象**：机器人沿路径由东向西、终点在北侧高台上，路径序列是"左转 → 上楼梯 → 右转"。
机器人在**楼梯立面前**原地不动，不上台阶。

**已核实的相关事实**：

| 事实 | 位置/数据 |
|---|---|
| 楼梯是 5 级 × 0.2 m，踏面 0.4 m（`max_height_diff` 0.25 m → PRM 判为可通过） | `docs/phase0_baseline_report.md` §2 |
| **楼梯弦不会被判不可通行**：`segment_passable` 是沿 Bresenham **逐格**比较相邻格高差，跨一级只有 0.2 m ≤ 0.25 | `prm.py:252-270`；离线实测见下 |
| 干净 eval 的 stairs 分档是新策略最差的一档：SR **0.122**（旧策略在 legacy 路径下 0.403） | §6 表格 |
| 本地路径观测是 `(direction_xyz, log 距离)` 15 点 × 4 = 60 维，**含 z 方向** | `observations.py:514` |
| 全局路径 15 点覆盖 20–40 m，楼梯只有 2 m 长、1 m 高，**全局路径在楼梯上可能只有一个点** | `num_smooth_points=15` |
| 位置奖励按**弧长**付，上下楼梯时水平位移小、弧长增量小 → 单位时间收入比平地低 | `path_generator._v2_path_metrics` |

**离线实测（`scripts/probe_path_geometry.py`，不启动 Isaac）**：

| 场景 | invalid 段 | pinch 段 | 跨楼梯弦的最大逐格高差 |
|---|---:|---:|---:|
| 平地走廊 | 0 / 14 | 0 / 14 | 0.00 m |
| 5 级 × 0.2 m 楼梯 | **0 / 14** | 0 / 14 | **0.20 m** ≤ 0.25 |
| L 形 90° 拐角 | 1 / 14 | 2 / 14 | 0.00 m（拐角处 clearance 0.30 < 0.31） |

→ **楼梯的路径几何是干净的，"停在楼梯前"不是路径判错**。`invalid_seg_frac = 0.22` 的来源是拐角处的贴墙弦
（重采样把 clearance 压到门限边缘），与楼梯无关。另外，LOS 会把楼梯段的 z 插值成一段缓坡而不是台阶剖面，
所以**局部路径观测不会告诉策略"前面是楼梯"**。

**假说排序**（先说清楚哪个更可能）：

1. **准备动作没有收益——与 §10.1 是同一个机制**（最可能）。真实的上楼梯是"先摆正、再加速冲台阶"；
   摆正/调整这段时间 `d_path` 会短暂变大、`progress_along_path` 为 0，还要付动作代价。
   v2 把路径做得"很严格"（0.5 m 走廊 + 0.8 m 支付门），恰恰惩罚了这段必要的准备动作。
   旧策略不跟路径，可以退两步重新对准，所以它上得去（0.403 vs 0.122）。
2. **轮腿在斜向进近时物理上确实吃力**：需要先排除。B2W 的轮腿正对台阶（0.2 m 级高、0.4 m 踏面）
   是能上的；斜着切上去不一定。而路径在楼梯处是**贴着台阶中线**走的，policy 被奖励逼成正面硬顶。
3. **`dir_z` 与"墙"的混淆**：**未排除**。路径 z 是折线插值——直走廊楼梯上 LOS 把整段压成一条弦，
   `dir_z ≈ 0.05`（像平路）；但若楼梯正好落在两个航点之间（"左转→上楼梯→右转"就是这种），
   一个 1.4 m 弦要吃 1.0 m 高差，`dir_z ≈ 0.6`，观测上接近"前方向上的墙"。需要在真实 tile 上量（D3b）。

**下一轮要做的**（详见 `docs/v1p1_next_plan.md`）：D1b —— 低层在不同进近角（0°/15°/30°）与速度
（0.2/0.5/0.8 m/s）下能否爬上 0.2 m 踢面。正对 0.5 m/s 都上不去 → 能力问题（先改地形/课程，不靠奖励硬修）；
只有斜向失败 → 是进近角问题（对应拐角弦切）。

**怎么确认**：
- 先看**速度与进度**：停住时 `‖v‖` 是否 ≈0、`progress_along_path` 是否连续 >1 s 为 0。是 → 假说 1。
- 再排除**物理**：同一 checkpoint、place 到楼梯正前方 1.5 m、给恒定前向指令 0.5 m/s，能上去 → 物理没问题。
- 再看**示教特征**：把 `get_path_local(6 m)` 前 3 点的 `(dir_x, dir_y, dir_z)` 打出来，z 是否异常大（假说 3）。
- 对照**平地同形状**：平地"左转-直行-右转"不停 → 楼梯特有；也停 → 是转弯/准备动作的通用问题（回到假说 1）。

**候选修复**（按假说 1 优先）：
1. **给"恢复进度"一次性奖励，而不是给"准备动作"每步奖励**：例如 `progress_along_path` 在停滞 >1 s 后的
   第一次正进度加一个小倍率。它不产生"站着就有钱"的面，但让"动起来"这件事有梯度。
2. **楼梯课程**：先在平地练"转弯-直行-转弯"，再混入带楼梯的 tile（当前 stairs 与其它 tile 一起随机采样，
   模型没有单独练过这一族几何）。
3. 若量测确认 `dir_z` 异常（假说 3）：把本地路径的 `dir_z` 压成坡度角单独一维，避免与"朝向墙"混淆。

> 这两条**不是 P1 的替代品**：P1 关掉的是"目标附近刷分"，而这两条是"连目标都到不了"。
> 但 P1 修完之后，§10.1 的僵住会变得更刺眼（原来僵在目标附近还能蹭 0.84/步，之后一分没有），
> 所以建议 **P1 与 10.1 一起进下一轮训练**，10.2 先量测再决定。
